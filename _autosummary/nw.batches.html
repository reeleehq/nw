nw.batches#

nw.batches — many jobs, one handle: submit / status / wait / output / cancel.

An agent driving a 200-shot fan-out should not burn a turn per poll and track N job ids (reelee#261 B). A batch is a small durable record beside the job records (<jobs_dirname>/batches/<batch_id>.json: batch_id, the ordered job_ids, a label, created_at). Everything else is *computed from the member jobs on read* and never stored, so a batch cannot drift from its jobs:

  • enqueue_batch() enqueues each item through nw.jobs.enqueue(), so idempotency, ETA, cost, heartbeat and the reaper stay per-job and unchanged. The batch_id is a pure function of the ordered job ids, so re-submitting the same batch returns the same batch (and, per job, the same live jobs).

  • status() — counts per job status, summed cost, done.

  • wait() — blocks until every member is terminal or timeout elapses, then returns the current aggregate with timed_out. Distinct from status(), which never blocks. Woken by the project’s nw.jobs.JobNotifier

    (job finish / cancel) and re-checking at poll_s regardless, because the reaper and cross-process workers change a job without notifying anyone here.

  • output() — a partially failed batch yields its successes and its failures, never an all-or-nothing error.

  • estimate_batch() — the cost gate: the sum of per-item nw.jobs.estimate(); an unknown item makes the whole batch unknown and

    therefore approval-requiring (None is never free).

  • cancel_batch() — cancels every non-terminal member (job cancel is idempotent and a no-op on a finished job).

Items are mappings {"kind": ..., "params": {...}} (optionally label, idempotency_key, and estimated_usd — a host’s own price for that member, kept out of its job id, nw#144); a batch-level kind= is the default for items that omit one. Item identity should be semantic (see nw.transforms.fanout’s mapping_key): the default idempotency key hashes params.

Cost gating of the spender (a per-caller cap) belongs to the host’s enqueue door, exactly as for a single job; this module adds only the dry-run.

Enqueue every item as a job and record the batch. Never blocks.

enqueue_kwargs (dispatch, on_event, secrets, capture_context, backend) go to each enqueue call unchanged. Every item is validated (keys, kind in dispatch, units) before the first one launches, so a bad item leaves nothing running. Re-submitting a batch that exists returns it without enqueueing.

enqueue (default nw.jobs.enqueue(), called with the same arguments) is the seam for a host’s own single-job door, so a batch member is enqueued exactly as a lone job would be. It must enqueue the job the item names (it may add server-side params only if they do not change the job id): a returned job whose id differs from the item’s raises ValueError and no batch is recorded, because the record would point at the wrong job. That is a host bug, so it is raised loudly, not repaired: the members enqueued before it keep running, and a retry may relaunch the ones that have finished (and bill them again). With a custom enqueue and no dispatch, the up-front kind-in-dispatch check is skipped: the door owns its dispatch, so it owns that check.

Items resolving to the same job collapse to one member (first position wins). An enqueue_kwargs key that is also an item key (ITEM_KEYS), or an item estimated_usd that a custom enqueue does not accept, raises TypeError before anything launches, rather than on a later member after the first ones are running.

Block until the batch is done or timeout seconds pass (a hard cap).

timeout must be >= 0. Wakes on job finish/cancel via the project’s nw.jobs.JobNotifier (managed backend only; a custom backend= falls back to the poll_s re-read).

Returns the status() aggregate with timed_out True when the cap hit first, so a caller can loop on it. None if the batch is unknown.
